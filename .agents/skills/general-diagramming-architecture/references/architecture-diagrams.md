# Architecture Diagrams

Canonical policy for system architecture diagrams that are generated by a
committed program rather than drawn. Owned by
[general-diagramming-architecture](../SKILL.md).

## What the Diagram Must Encode

A diagram that only names components duplicates the directory listing. A useful
one carries four things, and a component that has none of them does not belong
on the page.

| Element | What it must say |
|---|---|
| Component | What it is, and the decision or boundary it owns |
| Responsibility lines | Two to four phrases, taken from the design document's own words |
| Band | The party that owns the components inside it — the unit that could be swapped for another |
| Edge | The interface: what crosses, in which direction, over what transport |

Two rules keep the content honest:

- **Ownership over call order.** Bands are parties, not pipeline stages. "Who
  decides" and "who executes" being different bands is the most valuable thing
  a diagram can show; a left-to-right sequence of function calls is the least.
- **No invention.** Every role line traces to a sentence in the source
  document. If the diagram knows something the document does not, one of the
  two is wrong — fix that before drawing.

## Bands

Give the diagram three to five bands, ordered by authority rather than by data
flow. A common and durable arrangement:

1. **Authorship** — who decided what should be built, above the system
2. **Control** — who admits work, provisions, and holds custody
3. **Runtime boundary** — the process, container, or trust boundary, with its
   internal components and its state
4. **Interfaces** — the routes and contracts, listed as text

Band 4 is what makes the picture usable as a reference instead of a poster. A
reader looking up "how do I cancel a running job" should find the answer on the
diagram.

## Generated, Not Drawn

| Rule | Reason |
|---|---|
| The generator is the source of truth; the SVG is build output that is committed | The SVG is reviewable in a PR and renders in Markdown, but is never hand-edited |
| The SVG carries a banner comment naming its generator | The next person to open it will otherwise edit the wrong file |
| The generator exposes `--check` and CI runs it | A design change that does not regenerate the picture must fail, not merge |
| No diagram library, no layout engine | Auto-layout moves boxes when content changes, so review diffs become unreadable and the ownership grouping is lost |
| No external fonts, no remote assets | The file must render identically in CI, in a PR view, and offline |

Hand-routing is affordable up to roughly 40 nodes. Past that the diagram is
trying to say too much; split it.

## Composition

Build from a small set of primitives — text, band, tab, card, edge — and
declare components as data. Two structural rules do most of the work:

- **One shared column grid** across the bands whose components connect. Edges
  between layers stay straight because the boxes they join share an x centre,
  not because anything routed them.
- **Reserve gutters.** Leave 30–45px between bands and beside the outermost
  column. Edge labels and orthogonal routing need somewhere to live; without a
  gutter every label lands on a border.

## Typography and the Fit Budget

SVG does not measure, wrap, or clip text. A line that is too long silently
leaves its box, and nothing in the toolchain complains. The generator must
therefore assert fit at build time.

Estimate the advance width per character as a fraction of the font size:

| Style | Fraction of font size | 13px example |
|---|---|---|
| Sans regular | 0.55 | 7.2px per character |
| Sans bold (titles) | 0.60 | 7.8px per character |
| Monospace | 0.60 | 7.8px per character |

Budget: `usable = box width − 2 × padding`, minus the badge column when a card
has one. Characters available are `usable ÷ advance`. Measured system-sans text
lands nearer 0.52, so these numbers are deliberately pessimistic — when the
assertion trips on a line that would in fact have fitted, shorten the line
anyway. You have no measurement, only headroom.

Related rules:

- Two font sizes for body text, at most. Size differences that are not
  meaningful read as noise.
- Keep titles under about 25 characters; a wrapped title needs manual line
  breaks that will be wrong at the next edit.
- Set an explicit `font-family` stack of system fonts. The default serif is
  wider than anything the budget assumed.

## Edges

An edge means one specific thing, and its appearance says which:

| Kind | Convention |
|---|---|
| Control / command | Solid, accent colour, arrowhead toward the receiver |
| Execution / delegation | Solid, second colour, one line per direction when both matter |
| Data or filesystem | Dashed |
| Best-effort / advisory | Dotted, and labelled as best-effort |

Rules:

- **A legend is mandatory** the moment there is more than one edge kind.
- **Two directions, two lines.** A double-headed arrow labelled with both
  payloads is unreadable; draw one line down and one up, 30px apart.
- **Route orthogonally through gutters.** Diagonals across a dense band cross
  content that a reader then has to visually untangle.
- **Label the transport, not the verb.** `TCP HTTP + bearer` tells a reader
  something; `sends` does not.

## Failure Modes

The specific ways generated diagrams break, and the rule that prevents each.

| Failure | How it shows up | Rule |
|---|---|---|
| Non-deterministic output | `--check` fails immediately after a successful write | Never iterate a set or any hash-ordered collection; no timestamps, random ids, locale-dependent formatting, or filesystem ordering |
| Collapsed whitespace | Space-padded columns render ragged | XML folds runs of whitespace. Emit two text elements at fixed x, or set `xml:space="preserve"` |
| Unescaped text | The file fails to parse, or a label vanishes | Escape `&`, `<`, `>` in every emitted string — component names contain generics, paths contain `<binding>` |
| Text overflow | A line runs past its box | Assert the fit budget at build time; treat a failure as a content problem, not a width problem |
| Band title collision | The first vertical edge entering a band crosses its title | Render band titles as a tab occupying part of the width, and route inbound edges outside the tab's x-range |
| Caption collision | A right-aligned caption sits under an edge | Bound captions to a column edge rather than the band edge |
| Crooked cross-layer edges | Arrows wander a few pixels off vertical | Share one column grid between the bands that connect |
| Missing fonts | Text reflows or clips on another machine | System font stack only; no `@font-face`, no remote fetch |
| Unknown background | Invisible in a dark-theme viewer | Paint an explicit background rect, or provide both themes via `prefers-color-scheme` |
| Decorative colour | A reader cannot tell a control call from a file write | Colour encodes edge kind and band identity, nothing else |
| Silent drift | The diagram outlives the design it documents | `--check` in CI, and the source document links to the diagram |
| Reviewed as source | Collisions ship | Rasterize and look at the image before every commit |

## Accessibility

- `role="img"` with `aria-labelledby` pointing at a `<title>` and a `<desc>`.
- `<title>` names the diagram; `<desc>` describes the bands and what crosses
  between them, so the content survives without the picture.
- Do not rely on hue alone to separate edge kinds — vary dash pattern too.

## Verification

1. Run the generator twice; the bytes are identical.
2. Run `--check` against the committed file; it passes.
3. Rasterize (`rsvg-convert -w <width> in.svg -o out.png`) and view the raster.
4. Read the diagram against the source document: every role line traces back.
5. Confirm the source document links to the SVG and the SVG names its
   generator.
